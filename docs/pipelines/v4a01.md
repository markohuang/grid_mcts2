# Pipeline v4a01 — first 8×8 pipeline (planned)

**Pipeline id:** `v4a01`
**Status:** pre-launch — bootstrap data not yet collected
**Map class:** MAPS[5] — 8×8 board, 20 qubits, 5 layers, 6 gates/layer, 60-step episodes
**Bootstrap source:** FakeNet selfplay wave `v4a_gumbel` (to be run first)
**Parent checkpoint:** none (fresh start; v3a01 weights are 5×5-specific and incompatible)

## Hypothesis

H: Does the v3a01 pipeline design (warm-start self-play + synchronous training) transfer to 8×8 boards, where the action space is 2.6× larger (64 vs 25) and episodes are 2.5× longer (60 vs 24 steps)?

The 5×5 result showed avg cost 22.1 → 12.99 (−41%) in 5 cycles. We expect slower per-cycle gains on 8×8 because the search space is much harder, but the same basic pattern should hold.

## Scale shift vs v3a01

| Axis | v3a01 (MAPS[2]) | v4a01 (MAPS[5]) | Factor |
|---|---|---|---|
| Board cells | 25 (5×5) | 64 (8×8) | 2.6× |
| Qubits | 12 | 20 | 1.7× |
| Layers | 3 | 5 | 1.7× |
| Gates/layer | 4 | 6 | 1.5× |
| Episode length | 24 steps | 60 steps | 2.5× |
| Action space | 25 | 64 | 2.6× |
| Legal actions at step 0 | ~14 | ~45 | 3.2× |
| Gumbel m (num candidates) | 14 | 45 | 3.2× |

At 10k sims and m=45, halving round 1 gives each candidate `floor(10000 / (45×6)) ≈ 37 sims` — much less than the 178 sims/candidate on 5×5 (m=14). Q-estimates in round 1 will be noisier. This is the core scaling challenge.

## Step 3: pipeline kickoff (10 cycles — pending fast+GPU smoke for games_per_task)

**Plan: 10 cycles, right-sized selfplay → buffer alignment.**

The core principle: generate exactly as many games per cycle as the buffer can hold (each game evicted by the next cycle is wasted compute). 8×8 transitions are ~60KB each, so buffer capacity is RAM-limited:

| Training RAM | Max buffer_size | Games that fit (60 steps/game) |
|---|---|---|
| 64G | ~600k | ~10k games (1 cycle) |
| 128G | ~1.5M | ~25k games (2.5 cycles) |

We target `--train_mem=128G`, `buffer_size=1500000` (90GB, comfortable headroom). Selfplay generates 25k games/cycle → each cycle exactly fills the buffer. Over 10 cycles, the sliding window accumulates history; the shuffled loader samples representatively from all cycles in scope.

**Kickoff command (update `--games_per_task` after fast+GPU smoke):**

```bash
python pipeline_kickoff.py \
  --pipeline_root=/scratch/huang651/grid_mcts2/pipelines \
  --pipeline_id=v4a01 \
  --bootstrap_data=/scratch/huang651/grid_mcts2/datasets/v4a_gumbel \
  --cycles=10 \
  --pretrain_epochs=2 --train_epochs=2 \
  --sliding_window=10 \
  --num_tasks=40 --games_per_task=TBD \
  --selfplay_time=06:00:00 --train_time=02:00:00 \
  --selfplay_cpus=64 --selfplay_mem=96G --train_mem=128G \
  --preset=hpc \
  --config_override=map_num=5 \
  --config_override=random_board=True \
  --config_override=mcts.num_simulations=10000 \
  --config_override=env.reward_mode=plan_cost \
  --config_override=mcts.root_dirichlet_alpha=0.1 \
  --config_override=mcts.gumbel.enabled=True \
  --config_override=mcts.backend=fast \
  --config_override=training.buffer_size=1500000
```

**Setting `--games_per_task` from the fast+GPU smoke (job 60008159):**
- Target: 40 tasks × games_per_task ≈ 25k games/cycle = 1.5M transitions
- games_per_task = 625, workers = 62 → 10 games/worker
- If smoke gives < 1500s/game: 10 games/worker × 1500s = 4.2h → fits in 6h ✓ → `--games_per_task=625`
- If smoke gives 1500–2500s/game: drop to 250 games/task (4 games/worker) → 10k games/cycle (buffer half-filled per cycle, still fine)
- If smoke gives > 2500s/game: drop sims to 5k or move to 256G train node

## Sizing notes

**Memory math:** 8×8 feature tensor `(6,64,20)×float32 = 30KB`; obs + bootstrap_obs = 60KB/transition. 1.5M × 60KB = 90GB. With model (~2GB), gradients (~2GB), OS/scratch: 128G node is fine. 256G if we want buffer_size=3M (full sliding-window-5 coverage).

**Selfplay calibration:** Fast+GPU smoke (job 60008159, classic baseline 3112s/game) will tell us the actual speedup. Amdahl ceiling is 3.7× (NN=73%), target 800–1200s/game. Games/worker and final games_per_task will be set from that result.

**Data loading:** Parallelized via `DataLoader(num_workers=32)` with `max_transitions` cap — loads only as many games as fit in the buffer (shuffled for multi-cycle representativeness). Expected < 60s vs previous 772s.

## What success looks like

Minimum viable (accept as baseline for further cycles):
- Cost distribution has `rel_cost_spread = (q90−q10)/median > 0.25`
- `corr(depth, cost) < −0.05` (Gumbel-adjusted — depth criterion is weaker, see selfplay_gumbel.md)
- Policy entropy between 1.0 and 3.0 (Gumbel fixed-σ should give ~1.5 at FakeNet, should stay healthy through cycles)
- Monotonic avg cost improvement across cycles 1→10

Stretch:
- By cycle 10, avg cost below the Kohei greedy baseline on 8×8 (need to compute Kohei on MAPS[5] val set first)
- Min cost below any known hand-designed bound for 8×8

## Key uncertainties

1. **Per-game wallclock on 8×8 with trained prior.** As the policy concentrates, trees get faster (v3a01 saw 664s → 537s from c1→c5). On 8×8 the prior may concentrate differently — hard to predict without data.
2. **Q-estimate quality at round 1 with m=45.** Only 37 sims/candidate in halving round 1 (vs 178 on 5×5). Elimination decisions in early rounds will be noisier. May need higher sim count (20k or 50k) for good quality on 8×8.
3. **Entropy trajectory.** v3a01 pUCT collapsed to 0.240 by cycle 5. Gumbel fixed-σ starts at ~1.571 and is more stable by design, but we haven't seen this through multiple pipeline cycles.
4. **Reward signal density.** 60-step episodes with plan_cost: the per-step reward signal is smaller relative to episode length. May need `reward_scale` tuning.
